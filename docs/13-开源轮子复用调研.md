# mda 可复用开源轮子调研（只读调研，2026-11-17）

> 任务：为 mda（纯 Python ARM64 静态+动态分析器，capstone + pyelftools + frida，通过 MCP 暴露）调研**可直接复用的开源轮子**。
> 约束：不加外部桥接、不拷专有源码（IDA 不行）；优先 pip 可装 / 清晰 API / 许可宽松；只调研不改代码。
> 方法：web_search / web_fetch 逐条核对官方 README、LICENSE、PyPI 元数据、GitHub API。所有 URL 均为实际访问过的证据来源。

---

## 〇、先说结论（TL;DR）

1. **能"真反编译 + CFG + 数据流"且纯 Python、许可宽松的只有一个：angr**（BSD-2，pip 可装，原生 AArch64/ELF）。代价是依赖重、Python 版本要卡准（mda 是 3.11 → 用 angr 9.2.x，不要 10.x）。
2. **密码算法识别几乎零成本就能补**：`yara-python`（Apache-2，pip）直接跑 `findcrypt-yara` 的 `findcrypt3.rules`（BSD-3）——规则文件是纯数据，不用 IDA。这是投入产出比最高的一项。
3. **符号执行最小可行组合**：`z3-solver`（MIT，pip）单独即可做约束求解；要"开箱即用的数据流/IR 符号执行"直接用 angr 自带的 claripy + SimEngine，不必另接 Triton。
4. **版本 diff 是最大的坑**：BinDiff 开源版（Apache-2）要 IDA/BinExport；Diaphora 是 AGPL-3 + IDA；Ghidriff 是 GPL-3 + 要装 Ghidra/JDK。**没有一个符合"纯 Python、无外部桥接"**——只能"参考算法自己写"（基于 mda 已有的函数表/call_graph 做函数级 hash 匹配）。
5. **OLLVM 反混淆**：`ollvm-unflattener`（Apache-2）和 `MODeflattener`（MIT）都是 Python，但底层都依赖 **Miasm（GPLv2）**——用了就意味着 GPL 合规义务；算法值得参考。
6. **pyghidra / r2pipe 本质都是外部桥接**（前者要 JDK+Ghidra 本体，后者要 radare2 二进制），与用户"不加外部桥接"的前提冲突，仅列为"参考"。

**最值得先接的 2-3 个（在"不引入外部桥接、尽量纯 Python"前提下）：**
> **① yara-python + findcrypt 规则（补算法识别，成本最低）**
> **② angr 9.2.x（补真反编译/CFG/数据流/符号执行，一次补齐最多缺口）**
> **③ 自己写函数级 diff（参考 Diaphora/ghidriff 思路，用 mda 已有的静态模型）**

## 一、mda 现状与缺口对齐（证据）

- 运行期依赖仅 `capstone==5.0.9` / `pyelftools==0.33` / PySide6 / mcp / frida，Python 3.11+（[requirements.txt](../requirements.txt)）。
- 官方自述边界："**只支持 ARM64**；**伪代码是结构化的，不是真反编译**；**没有数据库**"（[docs/script-mda-vs-ida.md](../docs/script-mda-vs-ida.md)），源码依据 `core/pseudocode.py`、`core/disasm.py` 的 `arch != 183` 校验。
- 用户列的需求逐条映射：
  | 用户缺口 | 最合适的轮子 |
  |---|---|
  | 真正反编译 | angr Decompiler（或 pyghidra/r2ghidra，但属外部桥接）|
  | CFG / 数据流 | angr CFGFast / ReachingDefinitions / VSA |
  | 混淆识别 | 无现成纯 Python 轮子；参考 ollvm-unflattener（依赖 Miasm）|
  | 版本 diff | 无合规现成轮子；参考 Diaphora/ghidriff 自己写 |
  | 调用图 | angr CFG + mda 已有 call_chain（mda 已较强，优先级低）|
  | 结构体推断 | angr 无直接能力；pyghidra 有（但要桥接）；`libdecomp` 可参考 |
  | 算法识别 | **yara-python + findcrypt 规则**（最佳）|
  | 符号执行 | **angr（自带 claripy/z3）** 或 z3 最小组合 |

## 二、结构化清单（按接入成本从低到高）

### 成本档 A：几乎零成本，pip 直装、依赖轻、纯数据/单一用途

#### 1. z3-solver — SMT 约束求解器
- **定位**：微软出品的位向量/算术约束求解器，符号执行的"发动机"。
- **解决缺口**：符号执行的最小可行底座（自己把 ARM64 指令翻成位向量表达式后求解分支可达性/输入）。
- **许可证**：**MIT**（PyPI `z3-solver` 5.4.1.0 元数据 `license: MIT License`）——最宽松。
- **安装复杂度**：低。`pip install z3-solver`，纯 Python wheel 含 native 库，无编译。
- **ARM64/ELF 支持**：与架构无关（它只解数学约束），ARM64 语义由调用方（mda 的 capstone）提供。
- **重量级依赖**：无。
- **建议**：**直接用**（若走"最小自研符号执行"路线）。不过 angr 已内置 z3，若接了 angr 就不必单独接。
- URL：https://github.com/Z3Prover/z3 ｜ https://pypi.org/project/z3-solver/

#### 2. yara-python + findcrypt-yara 规则 — 密码常量指纹识别
- **定位**：YARA 是二进制模式匹配引擎；`findcrypt-yara` 维护了一份**密码算法常量指纹规则库**（`findcrypt3.rules`）。
- **解决缺口**：**算法识别**（AES S-box、MD5/SHA 初始化常量等）——正是用户"常量指纹库"那条。
- **许可证**：`yara-python` **Apache-2.0**（PyPI 4.5.4 元数据 `license: Apache 2.0`）；`findcrypt-yara` **BSD-3-Clause**（GitHub API 确认）。
- **安装复杂度**：低。`pip install yara-python`；规则文件直接拿来 `yara.compile()`，与主程序解耦。
- **ARM64/ELF 支持**：与架构无关，直接扫整个 so 的字节；对 ELF 无需特殊处理。
- **重量级依赖**：无（yara 自带 native 库，wheel 现成）。
- **建议**：**直接用**。这是所有项里 ROI 最高的——规则是纯数据，完全不碰 IDA 或外部桥接，一个 MCP 工具即可暴露 `detect_crypto(so_name)`。
- URL：https://github.com/VirusTotal/yara-python ｜ https://pypi.org/project/yara-python/ ｜ https://github.com/polymorf/findcrypt-yara

#### 3. LIEF — ELF/PE/MachO 解析与改写
- **定位**：跨平台可执行文件解析/改写库（C++ 核心 + Python 绑定）。
- **解决缺口**：**版本 diff 的数据底座**（规范化两段 ELF 的节/符号/重定位）、**patch 写回**（mda 目前明确"不能 patch 二进制"）。ELF 解析本身 pyelftools 已够，LIEF 的增量价值是**改写**。
- **许可证**：**Apache-2.0**（[LIEF 仓库](https://github.com/lief-project/LIEF#license)）。
- **安装复杂度**：低-中。`pip install lief`，有各平台 wheel。
- **ARM64/ELF 支持**：完整支持 ELF（含 AArch64）解析与改写。
- **重量级依赖**：无（自带 native 库）。
- **建议**：**值得参考 / 按需直接用**。若 mda 只做只读分析，优先级低；若要做 patch 或规范化 diff，直接用。
- URL：https://github.com/lief-project/LIEF ｜ https://pypi.org/project/lief/

### 成本档 B：中等成本，pip 直装但依赖较重 / 需卡版本

#### 4. angr (+ cle + pyvex + claripy) — 一站式二进制分析平台 ★核心
- **定位**：UC Santa Barbara / Shellphish 维护的多架构二进制分析框架：反汇编+IR 提升、**符号执行**、**CFG（CFGFast/CFGEmulated）**、数据依赖分析、**VSA**、**反编译**。[官方](https://angr.io/) / [PyPI](https://pypi.org/project/angr/)。
- **解决缺口**：**一次补齐 5 项**——真反编译、CFG、数据流、符号执行、调用图（VSA/依赖分析还能辅助结构体推断）。
- **许可证**：**BSD-2-Clause**（PyPI `angr` `license_expression: BSD-2-Clause`，已核对元数据）——宽松，商用友好。
- **安装复杂度**：**中-高**。`pip install angr`。依赖很重：`cle` / `pyvex` / `angr-data` / `z3-solver` / `pypcode` / `capstone` / `networkx` / `lmdb` / `protobuf` 等一大串。
  - **⚠ 版本兼容关键**：mda 是 **Python 3.11+**。angr **10.x 要求 Python ≥3.12**（PyPI 10.0.7 元数据 `requires_python: >=3.12`）；**必须锁 `angr==9.2.x`**（9.2.170 元数据 `requires_python: >=3.10`，明确含 3.11）。这一点如果不卡，pip 会装不上或把 mda 环境带崩。
- **ARM64/ELF 支持**：**原生支持**。`archinfo.ArchAArch64` 明确定义 `pcode_id=AARCH64:LE:64:v8A`、`cs_arch=CS_ARCH_ARM64`、`vex_arch=VexArchARM64`（[archinfo 源码](https://docs.angr.io/projects/archinfo/en/v9.2.217/_modules/archinfo/arch_aarch64.html)）；官方首页列 ARM & AArch64。反编译经 `pypcode`（Ghidra SLEIGH 的 Python 端口）支撑 AArch64。
  - 补充证据：`angr-ghidra-core` 项目把 angr 的 Decompiler 接到 Ghidra 的反编译协议上，**在真实 headless Ghidra 上验证过 x86-64/ARM/Thumb/AArch64/MIPS/PPC32**（[仓库](https://github.com/angr/angr-ghidra-core)）——间接证明 angr 反编译对 AArch64 是工作的。
- **重量级依赖**：**是**（见上）。还会引入第二份 capstone（9.2.x 锁 capstone 5.0.3，mda 用 5.0.9 → 需注意版本共存）。
- **建议**：**直接用（首选，但要锁版本、做可选依赖隔离）**。建议做成**可选 extra**（`pip install mda[angr]`）而非硬依赖，避免把主程序环境搞重；用它补"当用户点名要真反编译/CFG/符号执行"时的深度分析。
- URL：https://github.com/angr/angr ｜ https://pypi.org/project/angr/ ｜ https://docs.angr.io ｜ https://angr.io/

#### 5. Miasm — Python 反向工程框架（IR / 反混淆 / 符号执行）
- **定位**：Quarkslab 出品的纯 Python 框架：PE/ELF 解析、x86/ARM/MIPS/**AArch64** 汇编与反汇编、**中间表示(IR)**、表达式化简/**自动去混淆**、符号执行、JIT 模拟。[README](https://github.com/cea-sec/miasm/blob/master/README.md)。
- **解决缺口**：**反混淆**（官方博客就有 "Deobfuscation: recovering an OLLVM-protected program"）、IR 级数据流/符号执行。
- **许可证**：**GPLv2**（README 首行 "free and open source (GPLv2)"）——⚠ 若并入 mda 分发，触发 GPL 传染义务，需评估合规性；作为"外部工具调用/参考算法"影响小。
- **安装复杂度**：中。`pip install miasm`（Python ≥3.10）；可选 extras：`[z3]`（z3-solver 4.16）、`[llvm]`（llvmlite）、`[cparser]` 等；纯 Python JIT 也能跑（慢）。
- **ARM64/ELF 支持**：确认有 `miasm/arch/aarch64` 架构模块（GitHub API 列目录：`aarch64, arm, mips32, ppc, x86...`），README 明列 "Opening/modifying/generating PE/ELF 32/64 LE/BE"。
- **重量级依赖**：中（可选 LLVM/z3；纯 Python 模式较轻）。
- **建议**：**值得参考算法自己写** 或"作为独立可选工具按需调用"。它的**表达式化简/去混淆思路**对 mda 最简单；但 GPLv2 + 与 angr 功能重叠，不建议同时深度集成两者。
- URL：https://github.com/cea-sec/miasm ｜ http://miasm.re

#### 6. Triton — 动态符号执行 / 污点分析框架
- **定位**：动态二进制分析库，动态符号执行 + 污点分析 + AST 语义 + SMT 简化，支持 x86/x86-64/ARM32/**AArch64**。[PyPI](https://pypi.org/pypi/triton-library/json) / [GitHub](https://github.com/JonathanSalwan/Triton)。
- **解决缺口**：符号执行、污点分析、去混淆（官方有大量 VMProtect/devirtualization 论文与工具）。
- **许可证**：**Apache-2.0**（[LICENSE.txt](https://github.com/JonathanSalwan/Triton/blob/master/LICENSE.txt)）。
- **安装复杂度**：**中-高**。`pip install triton-library`，但——⚠ **PyPI 现只有 x86_64 / win_amd64 / macos-x86_64 的预编译 wheel**（已核对 1.0.0rc4 全部 wheel 文件名，无 arm64）。mda 跑在 **Apple Silicon Mac** 上，`pip install` 会无对应 wheel，需 `git clone + cmake + make` 从源码编译（README 给了 macOS M1 的 `PYTHON_EXECUTABLE`/`PYTHON_LIBRARIES` 配置示例）。
- **ARM64/ELF 支持**：库本身支持 AArch64 ISA 语义（PyPI 描述原文 "AST representation of the x86, x86-64, ARM32 and AArch64 ISA semantic"）；但**本机安装要源码编译**。
- **重量级依赖**：是（libcapstone/libz3/可Boost/LLVM/Bitwuzla，均可选）。wheel 体积 22–56 MB。
- **建议**：**值得参考（论文/工具思路），暂不直接接**。功能与 angr 重叠，且 Apple Silicon 上 pip 装不了要编译，性价比低于 angr。若日后 mda 部署到 x86_64 Linux 服务器且强调动态符号执行，再重新评估。
- URL：https://github.com/JonathanSalwan/Triton ｜ https://pypi.org/project/triton-library/ ｜ https://triton-library.github.io/

### 成本档 C：高成本 / 与"无外部桥接"前提冲突，仅作参考

#### 7. pyghidra — 在 CPython 里调 Ghidra API
- **定位**：通过 JPype 在原生 CPython 中直接访问 **Ghidra** API，headless 跑分析/反编译。[PyPI](https://pypi.org/project/pyghidra/)。
- **解决缺口**：真反编译（Ghidra 级）、结构体推断、类型恢复、Version Tracking（diff）。
- **许可证**：**Apache-2.0**（PyPI 元数据）。
- **安装复杂度**：**高**。`pip install pyghidra`，但**必须另装 Ghidra 本体 + JDK**（Ghidra 起步要求 Java 25 JDK，[GettingStarted](https://github.com/NationalSecurityAgency/ghidra/blob/master/GhidraDocs/GettingStarted.md)；PyGhidra 3.0 要求 Ghidra ≥12）。通过 `GHIDRA_INSTALL_DIR` 指向安装目录。
- **ARM64/ELF 支持**：Ghidra 原生强支持 AArch64 + ELF，反编译质量业界顶级。
- **重量级依赖**：**极重（JVM + 整套 Ghidra）**——本质就是"外部桥接"，与用户前提直接冲突。
- **建议**：**不值得（在本约束下）**。除非用户放宽"不引入外部桥接"。可作为"如需 IDA 级反编译质量的唯一现实开源路径"记录在案。
- URL：https://github.com/NationalSecurityAgency/ghidra ｜ https://pypi.org/project/pyghidra/

#### 8. r2pipe + radare2 (+ r2ghidra) — radare2 脚本绑定
- **定位**：r2pipe 是 radare2 的 Python 管道绑定；r2ghidra 把 Ghidra 的反编译器（C++ 移植，**不需要 JVM**）嵌进 radare2，命令 `pdg` 出伪代码。[r2pipe](https://pypi.org/project/r2pipe/) ｜ [r2ghidra](https://github.com/radareorg/r2ghidra)。
- **解决缺口**：反编译（r2ghidra）、CFG、函数分析。
- **许可证**：`r2pipe` **MIT**（PyPI 元数据）；radare2 主体 **LGPL**；`r2ghidra` **LGPL-3.0-only**（[LICENSE.md](https://github.com/radareorg/r2ghidra#license)）。
- **安装复杂度**：高。`pip install r2pipe` 很容易，但**必须在系统里另装 radare2 二进制**（+r2ghidra 插件），仍是外部进程桥接。
- **ARM64/ELF 支持**：radare2/r2ghidra 支持 AArch64 + ELF。
- **重量级依赖**：是（radare2 原生工具链）。
- **建议**：**不值得（外部桥接）**，但 r2ghidra "把 Ghidra 反编译器单独抽出来、用 C++ 实现不依赖 JVM" 这个**架构思路值得参考**（对比 pyghidra 的重）。
- URL：https://github.com/radareorg/radare2 ｜ https://rada.re/n/r2pipe.html

#### 9. 版本 diff 三件套：BinDiff / Diaphora / ghidriff
- **google/bindiff**：**Apache-2.0**（2021 开源，[仓库](https://github.com/google/bindiff)），但**依赖 IDA Pro / Binary Ninja + BinExport 插件**（[binexport](https://github.com/google/binexport)）导出——专有工具依赖，不符合约束。
- **Diaphora**：**AGPL-3.0**（GitHub API 确认），最先进的免费 diff 工具，但**是 IDA 插件（要求 IDA ≥7.4，Python 3）**，也有 Ghidra 版本（[仓库](https://github.com/joxeankoret/diaphora)）。AGPL 是最强传染许可。
- **ghidriff**：**GPL-3.0**（GitHub API 确认），Python CLI 单命令 patch diff，但**依赖 Ghidra + JDK**（[仓库](https://github.com/clearbluejar/ghidriff) / [介绍](https://clearbluejar.github.io/posts/ghidriff-ghidra-binary-diffing-engine/)）。
- **解决缺口**：版本 diff。
- **建议**：**都不值得直接接**（要么专有依赖、要么 GPL/AGPL、要么要 Ghidra）。**值得参考算法**：函数级指纹匹配（地址无关 hash / 指令序列归一化 / 调用图同构）、基本块匹配、变更分级输出——用 mda 已有的 `functions` 表、反汇编缓存、`call_graph` 自己写一个 `diff_so(old, new)` MCP 工具，纯 Python、零新依赖。
- URL：https://github.com/google/bindiff ｜ https://github.com/joxeankoret/diaphora ｜ https://github.com/clearbluejar/ghidriff

#### 10. OLLVM 反混淆：ollvm-unflattener / MODeflattener
- **ollvm-unflattener**：**Apache-2.0**（GitHub API 确认），Python 工具，基于 **Miasm** 分析并恢复 OLLVM 控制流平坦化（[仓库](https://github.com/cdong1012/ollvm-unflattener)）。
- **MODeflattener**：**MIT**（GitHub API 确认），同样基于 Miasm 的 OLLVM 去平坦化（[仓库](https://github.com/mrT4ntr4/MODeflattener)）。
- **解决缺口**：deobfuscation（控制流平坦化）。
- **安装复杂度**：中-高（`pip install -r requirements.txt`，但依赖 Miasm→GPLv2 传递）。
- **ARM64/ELF 支持**：Miasm 层支持 AArch64；工具本身是否对 ARM64 平坦化样本验证过需实测。
- **建议**：**值得参考算法自己写**。许可证本身友好，但底层 Miasm 是 GPLv2，直接并入要注意；更现实的是把"识别 dispatcher + 恢复真实 CFG"的思路抽出来，用 mda 自己的 capstone + CFG 实现（mda 已有 `find_dispatch_tables` 工具，正好是去做这件事的底座）。
- URL：https://github.com/cdong1012/ollvm-unflattener ｜ https://github.com/mrT4ntr4/MODeflattener

#### 11. libdecomp — 轻量多架构反编译库（C）
- **定位**：MIT 许可的 C 库，内置 capstone 后端，**X86/X86-64/ARM64 开箱支持**反编译（[仓库](https://github.com/dmaivel/libdecomp)）。
- **解决缺口**：真反编译（轻量替代方案）。
- **许可证**：MIT。
- **安装复杂度**：高——**C 库，不是 pip 包**，需自己编译 + ctypes/cffi 封装。
- **ARM64/ELF 支持**：ARM64 反编译支持。
- **建议**：**值得参考，不值得直接接**（非 Python，违背"尽量纯 Python"）。若日后要极轻量反编译且接受编译，可考虑。
- URL：https://github.com/dmaivel/libdecomp

## 四、明确推荐组合（不引入外部桥接、尽量纯 Python）

### 第一优先（立即可做，成本最低、不碰依赖树）
**`yara-python` + `findcrypt-yara` 的 `findcrypt3.rules`**
- 补"算法识别"缺口；规则是纯数据、Apache/BSD 许可、pip 一行装。
- 落成一个 MCP 工具 `detect_crypto(so_name)`：编译规则 → 扫整个 so 字节 → 输出命中的算法常量与偏移 → 复用 mda 的 `function_at` 把偏移折回函数。
- 完全符合 mda 现有"静态查询"风格，不动主依赖。

### 第二优先（一次补齐最多缺口，做成可选 extra）
**`angr==9.2.x`（只用它的 CFGFast / Decompiler / claripy / z3）**
- 补"真反编译 / CFG / 数据流 / 符号执行"四项；BSD-2 许可干净、原生 AArch64/ELF。
- **务必锁 9.2.x**（Python 3.11 兼容；10.x 要 3.12），并做成 `pip install mda[angr]` 可选依赖，避免 capstone 5.0.3/5.0.9 版本冲突污染主环境。
- 定位为"用户点名要深挖时的可选引擎"，不替代 mda 自己的轻量伪代码。

### 第三优先（纯自研，零新依赖）
**参考 Diaphora / ghidriff 思路，用 mda 已有静态模型写 `diff_so(old, new)`**
- 版本 diff 没有合规现成轮子；但 mda 已有函数表、反汇编缓存、call_graph，天然适合做"函数级归一化 hash + 调用图匹配 + 变更分级"。
- 这是三个推荐里唯一"要写点代码"的，但完全可控、无许可风险。

> 组合理由：三者叠加覆盖了用户 9 项缺口中的 **算法识别、反编译、CFG、数据流、符号执行、调用图、版本 diff** 七项；剩下的"结构体推断、混淆识别"没有干净的现成轮子，建议继续用 mda 已有的 `search_insn` / `find_dispatch_tables` 通用能力演进（符合"通用能力铁律"，不为特定样本特调）。
