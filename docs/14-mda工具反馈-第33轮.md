# 使用反馈处理记录（第 33 轮）

来源：一位 AI 代理用 mda 分析加固 App（扁平化状态机 + vtable 间接调用 + Java 层）
后给出的 7 条反馈。本文逐条记录**核实结果**、根因与处理。

> 与第 32 轮（`docs/11-mda工具反馈.md`）的区别：那一轮偏动态调试，这一轮
> 全部是**静态分析**的可用性问题——"能看到但定位不回原文""函数边界不对"
> "Java 层完全没有"。

## 零、先纠正反馈里的一处事实错误（重要）

反馈原文第 2 条说「`discover_functions()` 有 **200 个硬上限**」。

**源码里没有这个数。** 核实后确认，200 来自三处与之无关的默认值：
`list_functions(limit=200)`、`find_dispatch_tables(max_tables=200)`、
`get_activity_log(limit=200)`。`discover` 的真实参数是 `max_rounds=6`。

使用者随后自行核对并撤销了这条，同时把真实问题替换为：

> **`discover_functions()` 只有两档，缺中间态**：默认只认 `bl_target`
> （某个 so 只补出 21~22 个，远不够）；`aggressive=True` 能补到数千个，
> 但会把 switch 的 case 块切碎。

这条是**真问题**，已处理（见第二节）。这条纠正本身也值得记录：
**报数字前必须回代码核实**，否则会把一个"列表截断"误判成"功能上限"，
后者会让人直接放弃这条分析线。

顺带修掉了这个误判的源头——`list_functions` 现在显式返回
`returned` / `truncated` / `limit`，并附带一句"这不代表函数表只有这么多个"。

## 一、问题 1 ✅ 成立 —— `function_at` 返回错误边界

### 反馈

```
function_at(0x1962cc) → addr=0x1962cc size=0x2b0 end=0x19657c
function_at(0x196424) → addr=0x1962cc size=0x2b0 end=0x19657c   ← 起点不符
```
而字节码证明 `0x196424: sub sp, sp, #0xe0` 是独立函数的完整序言。

### 核实

`function_at` 本身的二分逻辑没错（`elf_model.py:755`）。错在**函数发现**
没找到 `0x196424`：

- `0x1962cc` 只有 3 条指令就 `ret`，但它是一条 FDE 记录的 0x2b0 字节函数；
- `0x196424` 是**通过 vtable 间接调用**的，**没有任何 `bl` 指向它**；
- 默认档只认 `bl` 目标 ⇒ 它永远进不了函数表 ⇒ 被外层 FDE 区间整个罩住；
- `_refresh_functions` 只在「有更晚的入口」时才把宿主切开，所以切不了。

**这个根因和反馈第 5 条（没有 RELA/vtable 解析）是同一个**：间接调用的
目标既看不见、也发现不了。

### 处理

`discover` 补出中间档，判据从"序言"改成"**栈帧**"（见第二节）。

实测 `samples/libbase.so` 新增的两个入口：

| 地址 | 前置指令 | 前 3 条指令 | 有 bl 指向吗 |
|---|---|---|---|
| `0x1ad34` | `ret` | `paciasp` / `stp x29,x30,[sp,#-0x10]!` / `mov x29,sp` | **没有** |
| `0x1ade8` | `ret` | `paciasp` / `stp x29,x30,[sp,#-0x10]!` / `mov x29,sp` | **没有** |

正是反馈描述的形态。补入后 `function_at(0x1ad34)` 返回自身，不再返回外层。

## 二、问题 2（替换版）✅ 成立 —— 三档开关

### 核实：反馈对了一半

- 「必须紧跟终止指令」这个条件**源码里早就有**
  （`_scan_round`：`prev.mnemonic in _TERMINATORS`），不是缺的。
- 真正缺的是「**什么样的序言才算数**」。

旧判据 `is_prologue()` 把裸 `bti c` / `paciasp` 当函数序言。但它们是
**分支保护标记**，编译器给 switch 的**每个 case 块**都加了 `bti jc`。

实测首指令分布（libbase.so）：

| 形态 | 出现次数 | 判定 |
|---|---|---|
| `paciasp` \| `sub` \| `stp` | 152 | 真函数 |
| `paciasp` \| `stp` \| `str` | 76 | 真函数 |
| `paciasp` \| `stp` \| `stp` | 69 | 真函数 |
| `bti` \| `bfi` \| `mov` | 21 | **case 块** |
| `bti` \| `mov` \| `mov` | 17 | **case 块** |
| `bti` \| `adrp` \| `adrp` | 11 | **case 块** |

**分水岭是「后面跟不跟栈帧」，不是「有没有 bti」。**

同时验出旧档的真实污染：`aggressive=True` 在 libbase 新增的 **171 个入口
100% 是裸 `bti`**（前置 `b`×142 / `br`×19 / `ret`×10），即同一个 switch
的连续 case 块。

### 处理

`discover` / `discover_functions` / `build_xrefs` 统一改成三档，开关名按反馈
建议的语义命名（`aggressive` 保留为 `use_prologue` 的旧名）：

| 档位 | 等价调用 | 行为 | libbase 实测 |
|---|---|---|---|
| **bl_only** | 不传 / `use_prologue=false` | 只认 `bl` 目标 | 386 → 386（+0） |
| **strict**（推荐） | `use_prologue=true` | `bl` + 「终止指令后紧跟**完整栈帧**」 | 386 → **388**（+2，全是真函数） |
| **loose** | `use_prologue=true, strict_prologue=false` | `bl` + 任何序言（含裸 `bti`） | 386 → 557（+171，全是 case 块） |

两个开关都给时以 `use_prologue` 为准；归一之后的档位签名参与幂等判断，
所以 `aggressive=true` 与 `use_prologue=true` 不会被当成两个档位各跑一次。

严格档判据（`discover.is_frame_prologue`）只认三条栈帧建立指令：
`stp x29,x30,[sp,#-N]!`、`sub sp,sp,#N`、`stp <callee>,<callee>,[sp,#-N]!`。
裸 `bti`/`paciasp` 只作为可跳过的前缀，本身不算证据。

### 新增的三个自证字段

| 字段 | 含义 |
|---|---|
| `prologue_mode` | `off` / `strict` / `loose`，标明结果口径 |
| `skipped_loose_prologue` | 严格档**刻意不收**的裸 bti 候选数（不是失败） |
| `reached_max_rounds` | 跑满轮次仍未到不动点 ⇒ 该加大轮次，而不是认为已补完 |

### 顺带修掉的两个隐患

1. **换档位被幂等挡住**：`_discovered` 原来只按模块名记忆，导致"先用默认档
   跑过、再想换严格档"永远返回 `skipped`。现按
   `(模块, aggressive, strict_prologue)` 签名记忆，换档位会重新跑。
2. **`build_xrefs` 的 cached 分支不看档位**：已建图后传 `aggressive=True`
   直接返回旧结果，会误判"激进模式也没用"。现在返回
   `built_tier` 并在档位不符时给 `tier_mismatch` 与明确下一步。

## 三、问题 3 ✅ 成立 —— 伪代码没有源地址（本轮最卡人的一条）

### 反馈

```
伪代码中 'b.ne #0x1f7614' 出现 26 次
伪代码中 '// 0x1f7...' 形式的源地址注释：0 处
```
函数是扁平化状态机，26 个分支全跳回同一个分发器，
**26 行文本完全一致，无法对回源指令**。

### 核实

成立。`pseudocode.py` 只拼 `ins.text`，`ins.addr` 一次没用过。

**额外发现一个更大的问题**：文件头注释写着「分支生成 if/goto 框架」，
但代码里**根本没有这回事**——`_render` 只做三件事：调用换符号、数据引用
换字符串、`ret` 换 `return`，其余指令原样输出。

也就是说当前的 `decompile` 是**带符号替换的线性反汇编**，不是伪代码。
注释承诺过头了（本次已在工具描述里改写清楚：要真控制流用 angr 插件）。

### 处理

`generate(fn_addr, resolve=None, with_addr=True)`：

```
// liblog.so!create_android_logger @ 0x5020 (size 0x50)
// 20 insns, 1 bl, 15 shown, 5 skipped (frame only: ...)
void create_android_logger() {
    // 0x5028  stp x20, x19, [sp, #0x10]
    // 0x5030  mov w19, w0
    // 0x5034  mov w0, #1
    // 0x5040  calloc(...);  // bl #0xe040
    ...
}
```

`decompile` 工具同步加 `with_addr: bool = True`（体积敏感时可关）。

实测 `libbase.so` 里找到重复跳转目标 `0x1f180` 的函数，同一目标出现多次、
每行源地址前缀**互不相同**——正是反馈要的"页码"。

## 四、问题 4 ✅ 成立，但根因不是反馈以为的那个

### 反馈

> 真实 17 个 bl，伪代码里 16 个，漏了 `0x1f7ac8: bl #0x2d3e50`
> （`__stack_chk_fail`），且**没有任何提示**。

### 核实：不是渲染层丢的

`_render` 只对 `paciasp` / `autiasp` / `bti` / `nop` / 帧指针 `stp|ldp` /
`mov x29,sp` 返回 None，**`bl` 永远不会被跳过**。

真正原因是 **`disasm_function` 只解码 `fn.size` 字节**
（`disasm.py:69`）。`0x1f7ac8` 超出了 FDE 给该函数的 size 范围，
那条指令**从未进入解码**。所以"伪代码少了 bl"和问题 1 是同一族：
**函数边界不对**。

### 处理

1. 头部输出覆盖统计：`N insns, M bl, K shown, S skipped`，把「框架指令被
   省略」与「没解码到」分成两个数。
2. 末条既不是 `ret/b/br/brk`、也不是 noreturn 调用时，输出
   `WARNING 末条指令 0x... 是 ... ⇒ fn.size 可能被截断`，并给出继续
   反汇编的确切地址。

### 实现这个告警时踩的坑（值得记）

初版判据只有「末条是否属于 ret/b/br/brk」，结果**假警报率 43%~70%**：

| 样本 | 假警报 | 原因 |
|---|---|---|
| libbase | 269/386 (69.7%) | 末条是 `bl __stack_chk_fail` |
| liblog | 48/111 (43.2%) | 末条是 `bl __throw_length_error` |
| libcutils | 93/168 (55.4%) | 末条是 `bl abort` |

被调用者不返回，函数到此结束，**完全正常**。WARNING 一旦变成每三个函数
响两次的噪音，真截断那次就没人看了。

改成四档判据后降到 **0/0/0（含 libc 2754 个函数）**：

| 证据 | 判据 |
|---|---|
| ① | 末条是 `ret` / `b` / `br` / `brk` |
| ② | 末条是 `bl`，目标是已知 noreturn（名字名单 + `__throw_*` 等子串） |
| ③ | 末条是 `bl`，且 `末条地址+4` **正好是下一个函数入口**（边界精确的硬证据） |
| ④ | 都不满足 ⇒ 告警 |

判据 ③ 是实测发现的：libcutils `0xe57c` 的末条是 `bl 0xee48`，
而 `0xee48` 是无名 PLT 桩（符号已丢），靠名字永远判不出；
但 `0xe65c` 恰好是下一个函数入口，这本身就是"没有截断"的证明。

## 五、问题 6 ✅ 成立 —— `Function` 缺 `.start`

`Function` 字段是 `addr/size/name/end/contains`，按 IDA 直觉写 `fn.start`
会抛 `AttributeError`，而且文档里没列字段清单。

已加只读别名 `start`（与既有 `end` 对称）。`addr` 仍是唯一真实字段
（property 不进 dataclass fields，不会破坏序列化），避免出现两个可写入口
导致边界不一致。

## 六、问题 5 ✅ 成立 —— 无 RELA / vtable 解析

### 反馈

> 需求：找 `vtable[4] = 0x196424` 的调用点。实际过程是手写 Python 读
> `.rela.dyn`。mda 缺 `rela_query(addr_range)` 和 `vtable_resolve(addr)`。
> 这类「间接调用目标」恰恰是扁平化 + 虚函数样本的核心。

### 处理

新增 `server/core/rela.py`（1147 行）+ 三个只读 MCP 工具。

**两条解析路径，一个 walker**：节表路径（`.rela.dyn` / `.rela.plt` /
`.rel.dyn` / `.rel.plt`）与 `PT_DYNAMIC` 路径（`DT_RELA`/`DT_RELASZ`/
`DT_JMPREL`，含无节表的 dump so）只在「表偏移从哪来」上不同，逐条解码走同一份
`_walk()`——避免两份实现漂移（这个项目已经因为判据写两份而踩过坑）。

**addend 语义如实标注**：`addend_is_target` 只对 `R_AARCH64_RELATIVE` /
`IRELATIVE` 为真。`ABS64` / `GLOB_DAT` / `JUMP_SLOT` 的 addend 是附加到符号值上
的偏移，**不是最终地址**——把它们当代码地址喂进函数发现会造出一整批假函数。

### 顺手挖出的静默 bug（这才是最值得记的）

旧 `_parse_relocations` 写的是 `getattr(r, "r_addend", 0)`，但 pyelftools 的
`Relocation` 是**字典式容器**，没有 `r_addend` 属性 → **所有重定位的 addend
恒为 0**。

后果：1679 条 RELATIVE 的「目标函数地址」从来没被记录过。也就是说
**"vtable 指向哪个函数"这件事，mda 之前一直是失败的，只是失败得没有人察觉**
（字段存在、值为 0，看起来像"这里恰好指向 0"而不是"取错了"）。

已按字节直接解出真值。返回字段里加了 `addend_is_target`，让调用方不必记
哪几种类型能当地址用。

### 反喂函数发现（问题 1 与问题 5 的合流）

`code_targets()` 给出所有「addend 落在可执行段」的地址，`discover` 把它作为
**第三类入口证据**（与「被 bl 调用」同级）：

| 证据 | 来源 | 强度 |
|---|---|---|
| `bl_target` | 有 `bl` 直接调用 | 硬 |
| `rela_target` | 被重定位表当成代码指针（vtable / 函数指针表项） | 硬 |
| `prologue` | 终止指令后紧跟完整栈帧 | 启发式 |

实测 `samples/device/libc.so`：`code_targets=367`，其中 **6 个不在函数表**，
全部是 `bti c; mov x8, #N; svc #0` 形式的 **syscall 桩**——它们没有 `bl` 指向、
没有栈帧（叶子函数），所以 `bl` 目标与序言两条路都发现不了，只能靠重定位表。
打开 `use_rela` 后 6/6 全部收进函数表（`by_reason={"bl_target":48,
"prologue":43,"rela_target":5}`，第 6 个同时被 bl 引用）。

### 能力边界（必须知道）

**APS2 压缩重定位未解析**：`libbase` / `liblog` / `libcutils` 的 `.rela.dyn`
都是 APS2（`SHT_ANDROID_RELA`）+ `DT_ANDROID_RELA` 压缩编码，只有 `.rela.plt`
可解。所以这些样本 `code_targets=0`、`vtable_blocks=0`。

现代 NDK（r23+）默认打包就是 APS2 —— 也就是说 **vtable 反喂在这类样本上暂时
拿不到**。当前刻意不硬解：把压缩流当定长数组读会产出成批假条目（项目内
`dyn/jni.py` 有同样的踩坑记录）。`rela_summary` 里 `packed=true` 会如实标出。

### 新增工具

| 工具 | 用途 |
|---|---|
| `rela_summary(so)` | 先看这个：条目数/分布/code_targets/vtable 块数/边界与错误 |
| `rela_dump(so, from, to, kind, limit)` | 按地址区间与类别导出条目 |
| `vtable_at(so, addr)` | 是不是 vtable 项、第几项、指向哪个函数 |

实测 `vtable_at(0xfc040)`：

```
is_vtable: true
detail: vtable 块 [0xfc040, 0xfc0b0) 共 14 项，14 项指向可执行段；本项 index=0 -> 0x48140
target: 0x48140   function: sub_48140   at_function_entry: true
```

判定分三层（槽必须是 RELATIVE 的 r_offset / 块至少 2 项 / 块内 addend 落在
可执行段比例 ≥ 0.5），任一层不过都返回 `is_vtable=false` + 中文 `reason`，
不猜。

## 七、问题 7 ✅ 成立 —— 没有 dex（Java 层）能力

### 反馈

> 我被迫自己写 `dex_extract.py` + `dex_insn2.py`，踩了 4 个坑，**每一个都
> 导致过"看到不存在的东西"**（假 payload、假 native 调用、假 MessageDigest）。

### 处理

新增 `server/core/dex/` 包（6 个模块，只用标准库）+ 四个 MCP 工具：

| 模块 | 职责 |
|---|---|
| `reader.py` | 字节读取、ULEB128/SLEB128、路径 → 多个 dex 字节块（`.dex` 与 `.apk`） |
| `mutf8.py` | MUTF-8 解码（坑 1） |
| `header.py` | header_item 与 6 张 id 表、class_def、access_flags |
| `code.py` | `class_data_item`（坑 2）与 `code_item` |
| `bytecode.py` | 指令格式表（坑 3）与上下文相关的 payload（坑 4） |
| `api.py` | 四个公开 API + 多 dex 合并 + LRU 缓存 |

### 四个坑各自的处理

| # | 反馈原文 | 本实现 |
|---|---|---|
| 1 | ULEB128 是 UTF-16 字符数，不是字节数 | `string_data_item` 的 `utf16_size` 按 ULEB128 解，截断**按 UTF-16 单元计数**；`\xC0\x80` 与代理对单独处理 |
| 2 | method_idx 是增量编码 | `class_data_item` 的 `field_idx_diff`/`method_idx_diff` **累加**；direct 与 virtual 两个列表各自独立累加（实测不累加会出现整类几十个同名 `<init>`） |
| 3 | `move-wide/16` (0x06) —— **反馈这里的描述是错的** | 见下方纠正 |
| 4 | payload ident 只在紧跟 switch/fill-array-data 时才是 payload | 从 switch/fill 指令里带 offset 跳到 payload 才解析；顺序解码遇到 `0x0100` 无上下文按 `nop` 处理 |

### 反馈第 3 个坑的事实纠正

反馈写：

> `move-wide/16 (0x06)` 是 **21s 格式占 2 unit**，我记成 3 → 全线错位

**官方格式表里 0x06 是 `32x` = 3 code units。** 2 units 的是 `22x` 族
（`move/from16` 0x02、`move-wide/from16` 0x05、`move-object/from16` 0x16）。

所以"记成 3"其实是对的；真正容易混的是把 **0x06**（32x/3 unit）和
**0x16**（22x/2 unit）看串。本实现按官方表写，并在测试里**现场生成**一个
只含 32x 指令的 dex 与 dexdump 对拍（真实 apk 里的 classes.dex 一条 32x
都没出现，靠真实样本测不到这个格式）：

```
32x + invoke-custom：4727 条指令逐条一致
覆盖：{'0x2': 49, '0x3': 49, '0x5': 544, '0x6': 218, '0x9': 100, '0xfc': 1}
```

### 正确性验证：与 dexdump 逐指令对拍

本机有 Android SDK 的 `dexdump`，作为**第三方证据**：

| 项目 | 结果 |
|---|---|
| 索引表数量（string/type/proto/field/method/class_def） | 全部与 dexdump 一致 |
| 逐指令偏移 + 助记符 | **36650 个方法 / 563078 条指令，一致 563078 条（100%）** |
| payload 块 | 2723 块，全部按上下文正确识别 |
| code_item 集合 | 与 dexdump 一致 |

这不是自测——是拿 Google 官方工具的输出逐条对拍。

### 新增工具

| 工具 | 说明 |

## 八、过程中发生的一次事故（如实记录）

并行任务里，负责 dex 的子代理在一次写操作中把 `server/core/dex/api.py`
（23KB）覆盖成了 **24.9MB 的错乱内容**，原始源码丢失。

**处置**：

1. 立即中断该子代理。
2. 确认其余 5 个模块（reader/mutf8/header/code/bytecode）完好。
3. `__pycache__/api.cpython-311.pyc`（36KB，覆盖前编译）仍在 —— 这是唯一的
   完整副本。先按 sourceless import 恢复**功能**（126 项测试当时全过，
   证明 pyc 是完整版），再用 `marshal` + `dis` 从字节码里逐个还原函数
   签名、docstring、字符串常量与格式串，**重写源码**。
4. 重写后跑 `tests/test_dex.py`：**126 项全过，563078 条指令仍 100% 一致**——
   确认重建与原实现行为等价。

**遗留物**（需人工决定去留）：

- `server/core/dex/api.py.broken-24mb` —— 事故现场，24.9MB 垃圾，可删
- `server/core/dex/api.pyc` —— 应急用的 sourceless 恢复副本，源码已重建，
  可删（保留它会让人误以为有第二份实现）

**教训**：并行任务共享同一个文件系统，**一个大文件的 write 操作失败/写错，
没有 git 跟踪的新文件就没有任何恢复手段**。这类并行写要么先落盘到独立
文件再合并，要么该文件只允许一个执行者写。

### 事故后的第二发现：测试全过但功能是错的

重建后 126 项测试仍然全过，看起来"完全等价"。但做闭环验证时发现
**`dex_callers` 对真实 apk 里的任何方法都返回 `[]`**。

根因：`method_id_item` 是 `u2 class_idx / u2 proto_idx / u4 name_idx`，
**三个字段都该小端读**，而原实现里 `class_idx` 用了大端
（`(b0<<8)|b1`），`proto_idx`/`name_idx` 用了小端。同一结构体里混用两种
字节序，`class_idx` 永远对不上：

| 读法 | 在 RecyclerView$3 上匹配的条目数 |
|---|---|
| 小端（正确） | 2 |
| 大端（原实现） | **0** |

**为什么 126 项测试没抓到**：合成用例里目标类的 `type_idx` 恰好是 **0**，
`0x0000` 两种字节序读出来一样——这是字节序的天然盲区。
真实 apk 里 `type_idx=3973 (0x0F85)`，大端读到 `0x850F`，必然不匹配。

修法：`class_idx` 改小端读；并补一条**闭环回归测试**（`test_dex.py` 里的
`test_caller_roundtrip_real`）——先用 `dex_disasm` 抓一条 invoke 的目标，
再用 `dex_callers` 反查，调用者集合里必须包含刚才那个方法，同时**直白断言
该类的 `type_idx` 非 0**，确保这条测试真的踩在字节序上。

**教训（比事故本身更重要）**：
1. **"继承原实现"不等于"正确"**。重建时我照抄了字节码里的字节序写法，
   理由是"原实现如此"，结果把一个 bug 一起复制了过来。
2. **测试全绿不代表功能可用**。合成样本的 `type_idx=0` 是盲区；
   凡是"两种实现读出来一样"的边界值，合成测试天然覆盖不到。
3. **闭环验证比逐项对照更能发现断层**：`A 的输出 → B 的输入 → 结果回到 A`
   这种回路，比"逐条比对同一个函数的输出"更容易暴露两侧对同一事实的
   理解不一致。

## 九、测试与验证

新增四个测试文件，全量跑法：

```bash
.venv/bin/python tests/test_pseudocode_addr.py    # 问题 3、4、6      31 项
.venv/bin/python tests/test_discover_tiers.py     # 问题 1、2 + rela  53 项
.venv/bin/python tests/test_rela.py               # 问题 5           103 项
.venv/bin/python tests/test_dex.py                # 问题 7           131 项
.venv/bin/python tests/test_regressions.py        # 既有全量回归     1058 项
```

合计 **1376 项全过**（2026-11-18 实测）。

### 各套件里最关键的几条断言

`test_discover_tiers.py`：

- 严格档新增入口 **100% 是完整栈帧**（不许出现裸 bti）
- 严格档新增入口 **前置指令都是终止指令**
- 至少有一个新入口**没有任何 bl 调用者**（证明真能捞到间接调用函数）
- **被切分的宿主函数仍以合法收尾结束**——这条防的是最危险的误报：
  把一个大函数拦腰截断。libc/libbase/libcutils 上均为 0 例
- `use_rela=False` 时那 6 个 code target 仍未被覆盖、`use_rela=True` 后全部覆盖
- 函数区间补完后仍**互不重叠**

`test_pseudocode_addr.py`：

- 每行地址都 **4 字节对齐、落在函数区间内、能回查到原始指令**
- 同一跳转目标的多行，源地址前缀**互不相同**（这是"26 行一样"的判据）
- 头部声明的 `bl` 数 == 真实 `bl` 数（统计自己不能不可信）
- 正常样本上截断告警率 **0/0/0**（初版是 43%/69%/55%）
- 人为缩短 `fn.size` 后 WARNING 必须出现且指向正确地址

`test_rela.py`：另写一份只按 ELF 规格的独立解析 + pyelftools，三方逐项比对
`offset/rtype/sym_idx/addend/sym_name` 全等；抹节表样本 235/235 一致；
真壳 dump（`DT_NULL` 开头）返回明确错误而非空表或假条目。

`test_dex.py`：与 `dexdump` 逐指令对拍 563078 条 100% 一致；四类坑各有
独立用例；32x 族因真实样本里一条都没有，靠**现场生成 dex** 验证；
另有 5 项**闭环**断言（从反汇编抓一条 invoke 目标，再用 dex_callers 反查回来）。

### 两个测试的"负向"设计（比正向断言更重要）

1. **禁令式断言**：不是"应该包含 X"，而是"**不许出现 X**"。
   例如"新增入口 100% 是完整栈帧"、"宿主不许被切成非法收尾"、
   "use_rela=False 时不许出现 rela_target 依据"。
   只看正向断言的话，一个过度激进的实现也能全绿。
2. **假警报率断言**：`test_pseudocode_addr` 直接统计整库告警比例并断言为 0。
   这条防的不是"功能缺失"，而是"**功能存在但输出全是噪音**"——
   后者比前者更难发现，因为工具看起来在工作。

## 十、这次改动对老用法的兼容性

| 老调用 | 行为变化 |
|---|---|
| `discover(aggressive=False)` | 不变（只认 bl 目标） |
| `discover(aggressive=True)` | **变了**：默认走严格档（更少但更准）。要旧行为传 `strict_prologue=False` |
| `discover(...)` | 新增 `use_prologue`（`aggressive` 的语义化别名）、`strict_prologue`、`use_rela=True`；返回新增 `prologue_mode` / `use_rela` / `rela_targets` / `skipped_loose_prologue` / `reached_max_rounds` |
| `discover_functions` 重复调用 | 同档位仍幂等；**换档位会重新跑**（旧版换档位也被 skip） |
| `decompile(so, addr)` | 输出多了每行地址注释与头部统计；`with_addr=False` 可退回旧格式 |
| `fn.addr` | 不变；新增只读别名 `fn.start` |
| `list_functions` | 返回值新增 `returned`/`truncated`/`limit`/`truncated_hint`，`functions` 语义不变 |
| `so.relocations[].addend` | **变了（修复）**：以前恒为 0，现在是真实 addend |
| rela / dex 工具 | **全新**，不影响任何既有调用 |

`aggressive=True` 的默认行为变化是有意的：旧档的产出**100% 是 case 块误报**
（libbase 实测），继续默认保留它等于默认给错误答案。

`so.relocations[].addend` 的变化也是修复：字段一直存在但值恒为 0，
"看起来像这里恰好指向 0"而不是"取错了字段"——这类错误最难察觉。

## 十一、还没做的（下一轮的候选）

| 项 | 影响 | 建议 |
|---|---|---|
| **APS2 压缩重定位**（`SHT_ANDROID_RELA` / `DT_ANDROID_RELA`） | libbase/liblog/libcutils 及现代 NDK（r23+）默认产物**拿不到 vtable**，`rela_target` 这条证据对它们无效 | 单独一轮做，必须用真实样本做不变量校验（offset 落在可写段、addend 落在镜像内、count 与 header 一致） |
| **RELR**（`DT_RELR`） | 只编码写入地址、不含 addend，需与同时代的 RELATIVE 表配合才能还原目标 | 同上 |
| **伪代码真正的 if/goto 结构** | 现在是"带符号替换的线性反汇编"。加了地址注释后能对回原文，但没有控制流嵌套 | 需要 CFG + 支配树；工作量大，可先用 `angr` 插件过渡 |
| **非 ARM64** | `Disassembler` 只支持 AArch64 | 现状如实报错，不假装支持 |
