# 跨进程注入能力 —— 技术报告与实测记录

> 目标：使用者在 48 轮逆向中卡在「知道该看哪里，但总是看晚了」。
> 需要「写入发生的那一刻，把写入前的内容和现场留下来」。
> 本文档记录为实现该能力所做的**全部实测**，包括走通的与没走通的。

设备：`3e2ff172`（M2002J9E / Android 12 / arm64 / 内核 4.19.113 / Magisk root / frida 17.23.3）

---

## 一、为什么不用 frida

frida 已在目标进程里，看起来应该最方便。但实测两条路都不通：

| 方案 | 实测结果 |
|---|---|
| `MemoryAccessMonitor.enable()` | **直接把目标进程搞崩**（system_server 消失、Android 框架整体重启） |
| `Process.setExceptionHandler` + mprotect | handler **收不到** SIGSEGV；目标直接被系统 crash handler 接管 |

第二条是本轮的关键实验（`tests/manual_mprotect_frida.py`）：

```json
{"results": {"protect_ok": true}}      ← Memory.protect 成功，页确实变只读了
→ 目标进程随即崩溃（session is gone）
```

**frida 侧做不了 mprotect+SIGSEGV 捕获**。

而**纯用户态 C 程序**做得到（`/data/local/tmp/t_sigh` 实测）：

```
about to write read-only page 0x7eb76cd000
[handler] sig=11 si_addr=0x7eb76cd000
  uc+0x0b0 fault_address
  uc+0x0b8 regs[0]
  uc+0x1a8 regs[30]
  uc+0x1b0 sp
  uc+0x1b8 pc
after write, got=1  first byte=Z
```

**注意一个曾经导致误判的细节**：
访问**完全无效**的地址（0x12345678）时内核直接处理，用户态 handler 拿不到；
访问**有效但只读**的页才会正常触发 handler。
两者混为一谈，会得出"用户态 SIGSEGV handler 不可用"的错误结论。

**ucontext 偏移（ARM64，实测值）**：

| 字段 | 偏移 |
|---|---|
| fault_address | `uc+0x0b0` |
| regs[0] | `uc+0x0b8` |
| regs[1] | `uc+0x0c0` |
| regs[30] (lr) | `uc+0x1a8` |
| sp | `uc+0x1b0` |
| pc | `uc+0x1b8` |

## 二、跨进程注入：走通了的部分

用 ptrace 把代码注入目标进程。**以下能力全部在真机验证通过**：

### 1. ptrace attach / detach

```
selftest → {"ok":true,"attached":true,"rw_page":"0x7afcedc000","vm_read":true}
```

### 2. 跨进程读内存

`process_vm_readv` 正常。

### 3. 跨进程写内存 —— **必须用 PTRACE_POKEDATA**

```
process_vm_writev：返回成功但**根本没写进去**（readback 全 0）
PTRACE_POKEDATA ：readback 完全匹配 ✓
```

**原因**：目标处于 ptrace stop 状态时，`process_vm_writev` 对部分内存的写入
会被内核跳过，却照样返回字节数。这是典型的"假成功"。

### 4. 远程系统调用 —— 核心技巧

**做法**：不调用 libc 的 `syscall()` 包装，而是**直接跳到包装内部的 `svc` 指令**，
用 `PTRACE_SINGLESTEP` 跨过它，立刻读 x0。

```c
regs.x[8] = nr;          /* syscall 号 */
regs.x[0..5] = args;     /* 内核约定：x0..x5 是参数 */
regs.pc = svc_addr;      /* libc 里 svc 指令的地址 */
PTRACE_SINGLESTEP;
PTRACE_GETREGSET → cur.x[0]  /* 内核原样写入的返回值 */
```

**为什么不能走 `syscall()` 包装**：包装在 `svc` 之后有一段错误处理代码，
会**改写 x0**。实测读到的 `0x7ff665eb28` 不是页对齐的 mmap 返回值，
而是包装处理过的中间值。

**实测**：

```
getpid(172)  → x0 = 0x2cc8 = 11464 = 目标 pid ✓
mmap(222)    → x0 = 0x6fefdd8000（页对齐的有效地址）✓
```

**两个必须踩过的坑**：

| 坑 | 现象 | 解法 |
|---|---|---|
| `mmap2`(243) vs `mmap`(222) | mmap2 返回 EFAULT | 用 `mmap`(222) |
| fd 传 64 位 -1 | EFAULT | 传 32 位 `4294967295` |

### 5. 远程 mmap / mprotect

```
远程 mmap(222) → 0x6fefdc8000（RWX 页真实出现在目标 maps 里：rwxp）✓
远程 mprotect  → 把目标页改成只读，返回 0 ✓
```

### 6. libc syscall() 偏移必须可配置

不同 Android 版本的 bionic 里 `syscall()` 的偏移不同（本机是 `0x88190`）。
写死会让工具在别的 ROM 上直接失效 → 通过 `MDA_SYSCALL_OFF` 环境变量传入，
由 Python 侧从设备 libc 的 `.dynsym` 解析（`llvm-readelf --dyn-syms`）。

**顺带发现**：`adb exec-out` 拉下来的二进制是**坏的**（符号表读不出来），
必须用 `adb pull`。

## 三、走不通的部分（如实记录）

### 障碍 A：ptrace stop 状态下 rt_sigaction 返回 EINVAL

同样调用，普通 C 程序返回 0：

```c
syscall(134, SIGSEGV, act, NULL, 8)  →  0   ✓
```

但让目标在 ptrace stop 状态下执行同一条 svc → **-22 (EINVAL)**。

已排除的所有变量：
- act 结构布局（遍历 `flags_off=8..144 × rest_off` 逐个试，唯一可行是
  `handler@0x00 / flags@0x08 / restorer@0x10`）
- signo 漏传（曾漏，补上后仍 EINVAL）
- `sigsetsize`（8）
- `sa_restorer`（arm64 无 VDSO trampoline，必须自带）
- `SA_SIGINFO` / `SA_NODEFER` 各种组合（全部返回 0）
- act 放在栈上 / 共享内存 / 注入页的 .data（三处都 EINVAL）
- 代码地址是 libc 函数 / 匿名 RWX 页（两者都成功）

**绕过尝试**：用 `PTRACE_SYSCALL` 跟随目标自己的 syscall，在**入口**把参数换成
`rt_sigaction`，**出口**读结果 —— 这样内核走的是正常执行路径。
**这条路成功**（`rt_sigaction 成功, old_handler=0x0`）。

### 障碍 B：handler 装上了，但不被调用

即使绕过了 A（搭便车装 handler 成功、oldact 正常返回 0），
**信号处理器仍不被调用**：

```
tombstone: signal 11 (SIGSEGV) code 2 (SEGV_ACCERR) fault addr 0x50000000
  pc = t_rt (main+100)     ← 靶子自己的写指令
```

`SEGV_ACCERR`（而非 MAPERR）说明**页权限确实是只读的**（mprotect 生效了），
但写指令再次触发 SIGSEGV 时没有 handler 接住。

已排除：
- handler 代码地址在注入页里可执行（`readback` 校验一致）
- `bti c` 入口指令（4.19 内核无 BTI，但加上无害）
- handler 结尾用 `sigreturn`（139）而非 `ret`（ret 会触发 PAC 校验 → SIGILL）
- handler 不依赖共享内存（页地址/长度改用编译期常量注入）
- handler 极简化（只做 mprotect + sigreturn）
- Android runtime 是否抢 handler（实测 C 程序里装 handler 后**正常被调用**，
  且 `SigCgt` 装前装后都是 `0x4c400084f8`——**这个字段根本不能用来验证**）

**当前判断**：Android 12 / 内核 4.19.113 上，通过 ptrace 从外部给目标进程安装
信号处理器这条路，**在真机上无法使其生效**。原因未确定。

## 四、当前可用与不可用

### 可用（真机验证）

```
ptrace attach / detach
跨进程读内存   process_vm_readv
跨进程写内存   PTRACE_POKEDATA
远程系统调用   跳 libc 的 svc + 单步跨过，读内核原样返回值
远程 mmap      返回页对齐的有效地址
远程 mprotect  改目标页权限
```

**这本身就有价值**：可以在目标进程里执行任意 syscall，
而不只是被动观察（frida 做不到"在目标里调 mprotect"这类事）。

### 不可用

```
让目标安装 rt_sigaction（搭便车方式返回成功，但 handler 不被调用）
让目标在 ptrace stop 状态下调 rt_sigaction（EINVAL）
```

**因此**：「写入那一刻抓 before 内容 + 现场」这个目标，
**在本设备上尚未实现**。

## 六、复现命令

```bash
# 编译
cd server/dyn/device
python3 build_payload.py                       # 生成 payload 机器码
NDK=~/Library/Android/sdk/ndk/28.2.13676358
CC="$NDK/toolchains/llvm/prebuilt/darwin-x86_64/bin/aarch64-linux-android30-clang"
$CC -O2 -static -o mda_memguard_inject mda_memguard_inject.c mda_payload_bin.c

# 自检（验证远程 syscall 通路）
adb push mda_memguard_inject /data/local/tmp/
adb shell "su -c 'chmod 755 /data/local/tmp/mda_memguard_inject'"
adb shell "su -c '/data/local/tmp/mda_memguard_inject selftest <pid>'"
# → {"ok":true,"getpid_ret":<pid>,"remote_syscall":"works"}
```

**注意**：设备上做实验时用自己编译的小程序当靶子，**不要用系统进程**
（systemui / system_server 崩了会导致整机重启）。
