# 第 35 轮插件反馈：五个工具"有输出但给不出答案"

来源：一位 AI 代理用 mda 分析加固 App 后的反馈。这一轮和前面几轮不同——
**没有一个是崩溃或报错**，全部是「工具跑完了、有输出、但那个输出不是我要的答案」。

这类缺陷比崩溃更难发现：崩溃至少会告诉你"这里不行"，而空结果会被读成
"这里本来就没有"。

---

## 一、逐条核实

| # | 反馈原文 | 核实 | 根因 |
|---|---|---|---|
| 1 | `emulate_func` 不返回内存内容（只有寄存器和 trace） | ✅ 成立 | 返回结构里根本没有 memory 字段 |
| 2 | `call_graph` / `xref_enhanced` 找不到虚调用者 | ✅ 成立 | 两者都只认 `bl` 边 / `adrp+add` 数据引用 |
| 3 | `string_crack` 三种方法都不匹配 `.rodata` | ✅ 成立 | 三个独立 bug 叠加 |
| 4 | `sensitive_scan` 全是噪音（`/Y`、`/R`） | ✅ 成立 | 路径判据没有长度下限 |

反馈里同时点名了几个**工作正常**的工具（`decompile_c` 控制流分块与手工分析
完全一致、`emulate_func` 的 trace 显示出正确的「读/异或/循环右移/写」四轮循环、
`data_flow` 坐实 x19 全程未被写过、`xref_enhanced` 报零引用）。这些是交叉验证
成功，不需要改。

## 二、问题 1：`emulate_func` 不返回内存

### 为什么这最可惜

使用者已经把这个工具用对了——解密函数跑起来，trace 显示循环四次、每次都
「读、异或、循环右移、写」。**执行路径完全正确**，但结果写在缓冲区里，
而返回结构只有 `registers` / `stopped` / `trace`。

寄存器里通常只留一个指向缓冲区的指针。所以"跑通了"和"拿到结果"之间
缺了这一环。

### 处理

新增 `dump` 参数，四种模式：

| 值 | 行为 |
|---|---|
| `[{addr, size}, ...]` | 按指定范围导出（最常用、最精确） |
| `"writes"` | 只导出运行期间被写过的页 |
| `"stack"` | 导出栈区 |
| `"all"` | 导出所有已映射区间 |

`dump_max`（默认 4096）限制单段导出字节数，超出截断并标 `truncated` +
`full_size`，不会因为某个 100MB 段把返回撑爆。

每个 region 返回 `hex` + `ascii`（不可打印显示为 `.`）+ `strings`
（按 NUL 切、全可打印的片段）——后者是最实用的，解密结果几乎都是 C 字符串。

### 实现时的两个坑（都写进注释了）

**坑 1：「writes」模式的粒度取舍**

逐字节记录写操作会在循环里产生巨量回调。实测这个解密函数循环 4 次还行，
但换成大循环就会把模拟拖死。所以只记录**被写过的页号**，导出时给整页，
并在 `note` 里明确说"只精确到页，请按你已知的结构自己裁"。

**坑 2：`stack` 模式初版恒为空（两层原因）**

```
① 用「运行后的 sp」算已用长度 → 函数返回后 sp 已恢复，算出来接近 0
② 改用「入口 sp 到栈顶」→ 入口 sp 本身就等于栈顶：
   sp = stack_base + stack_size - 0x1000
   所以 top - entry_sp == 0，区间恒为空
```

实测 `liblog 0x5020`：`entry_sp = top = 0x7fff0000f000`。

正确理解是**栈向下生长**，函数用过的区域在 `[entry_sp - 已用, entry_sp)`。
改成导出 `[top - stack_size, top)` 整段，空的部分读出来是 0，
正好作为"这里没写"的证据。

## 三、问题 2：找不到虚调用者

### 为什么两者都找不到

调用图与引用扫描都建立在**指令操作数**上：

- `call_graph`：取 `ins.call_target`——这个字段只有 `bl <imm>` 才填
- `xref_enhanced`：扫 `adrp+add` / `adrp+ldr` 的 `ref_addr`，而且主动排除了
  `is_call` / `is_jump`（这个排除本身是对的，见第 32 轮的修复）

而虚调用长这样：

```
ldr x8, [x0, #8]     ; 从表里取出函数地址
blr x8               ; 跳过去——目标在寄存器里
```

**静态没有操作数可查**。实测 libc 有 6 个函数没有任何 `bl` 指向它们
（`bti c; mov x8,#N; svc #0` 形式的 syscall 桩），只被 vtable 引用。

### 处理：把重定位表当证据源

函数指针表的**内容**在重定位表里——`addend` 就是"这个槽指向哪个地址"。
这正是第 33 轮做的 `core/rela.py` 能回答的。

`call_graph` 新增：

- `vtable_edge_count`：全库 vtable 边总数
- `indirect_only`：**没人 bl 调用、只被函数指针表指向**的函数列表
- 每个节点的 `vtable_in`：指向它的槽地址
- `include_vtable` 开关（默认开，关掉后归零——证明这能力可控）

`xref_enhanced` 新增 `indirect` 一节：`slot` / `target` / `target_function` /
`block`（vtable 起止）/ `rtype`。

### 一个重要的语义选择

**把 vtable 边算作「入边」而不是「调用边」。**

`ldr x8,[x0,#8]; blr x8` 里，x0 来自哪里、运行时指向哪张表，静态**算不出来**
（要数据流 + 对象布局）。能确定的事实只有一条：「槽 S 里存着函数 F 的地址」。

所以工具不假装知道"谁调了 F"，而是回答：**F 的 incoming 里多一条
`vtable@0xfc040`**。这既诚实（有据可查），又正好回答使用者的问题——
"这个函数没有任何 bl 引用，它是被谁指向的？"

`note` 里写明了这个区别：`vtable` 边**不代表**已知道运行时谁真的调了它。

### 实测

```
libc.so: vtable_edge_count = 367
vtable_at(0xfc040) → 14 槽块 [0xfc040, 0xfc0b0)，本项 index=0 → 0x48140
xref_enhanced(mode=refs, addr=0x48140):
    refs.count = 0          ← 代码里确实没有 adrp 到它（正确，不掺假）
    indirect.count = 1      ← slot=0xfc040 → 0x48140 sub_48140
```

## 四、问题 3：`string_crack` 三个 bug 叠加

### 三个 bug 各自的作用

**bug ①：`addr+size` 路径不按 NUL 切块**

```python
if addr is not None and size:
    data = so.read(int(addr), int(size))
    out.append((int(addr), data))    # ← 整节 1992 字节当成一个 block
```

**bug ②：`_semantic_score` 见到 `'.'` 直接返回 0**

```python
if not text or "." in text:
    return 0.0      # ← 整块二进制里必然有不可打印字节，必然 0 分
```

两个 bug 叠加的效果：**256 个 XOR key 全部 0 分，一个都出不来**。
而那块 `.rodata` 里其实有 86 条正常明文。

**bug ③：只给 `addr` 不给 `size` 时，`addr` 被静默忽略**

退回全库扫描，调用方以为"只解了这一节"。实测 `scanned_blocks` 从 1 变 122。

### 处理

| bug | 修法 |
|---|---|
| ① | `addr+size` 路径也走 NUL 切分，与全库路径**共用同一个** `_split_nul` |
| ② | 不再一票否决，改成「不可打印占比 > 0.4 才归零」，否则按占比扣分 |
| ③ | 只给 `addr` 时自动取到该地址所在节的末尾（`_guess_len`）；取不到就返回 0 块，让 `scanned_blocks=0` 可见 |

### 顺带补的能力：`plaintext` 模式

排查过程中发现一个真实缺口：那 86 条明文**不是没扫到，是被主动跳过**——
`_split_nul` 的判据是「可打印度 >= 0.9 → 已经是明文，不需要解密」。

逻辑上没错，但工具缺了另一半：使用者想确认"这块里到底有什么、我是不是漏看了"，
却只有"解密"这一个入口。

所以新增 `plaintext` 模式，直接列明文块，**与解密结果分开返回**
（一个是"本来就是明文"，一个是"解出来的"，混在一起会让人以为明文也是解出来的）。

```
plaintext: True  → count=86，含 /proc/self/cmdline、persist.log.tag. 等
plaintext: 不给  → scanned_blocks=4, count=3（只有像密文的块被尝试）
```

### 端到端验证

```
明文: https://api.example.com/v1/sign
key:  0x5A
加密后交给 _try("single_byte_xor") → 解回原文，params={"key": "0x5a"}
```

## 五、问题 4：`sensitive_scan` 噪音

### 判据有多松

```python
path_re = re.compile(r"^(/[\w./-]+)$")     # ← 没有长度下限
```

二进制里任何一个碰巧以 `/` 开头、后接几个路径字符的 **2 字节片段**都算路径。
实测 `.rodata` 里 `_.-@,` 这种符号表碎片都能通过。

IP 判据同理：`\d{1,3}(\.\d{1,3}){3}` 允许每段 999，还会命中 `%d.%d.%d.%d`
这类格式串。

### 处理

| 项 | 新判据 |
|---|---|
| 路径 | 长度 >= `min_len`（默认 4）；斜杠分隔后最长段 >= 2（排除 `/Y`）；必须含字母数字（排除 `_.-@,`）；不能是纯十六进制 |
| IP | 每段 0..255 校验；含 `%` 的整串跳过（格式串不是地址） |
| 去重 | `dedupe`（默认开），同一字符串多处出现只留第一条 |
| 可见性 | 新增 `filtered` 计数（`path_too_short` / `ip_bad_range` / `ip_format_string`）——**让"少"是可见的，而不是悄悄丢了** |

实测对比（liblog）：

```
修复前：全是 "/Y" "/R" 这类 2 字符碎片
修复后：7 条真实路径 —— /dev/pmsg0、/proc/self/cmdline、
        /system/etc/event-log-tags、/dev/socket/logdw ...
```

## 六、测试

新增 `tests/test_plugin_fixes.py`（41 项）：

```bash
.venv/bin/python tests/test_plugin_fixes.py
```

**设计上的两个取向**：

1. **断言"必须能给出那个答案"**，而不是"函数不抛异常"。
   例如"单字节 XOR 能解回已知明文并给出正确的 key"——先手工加密一段已知
   明文，再要求解密路径能还原它。

2. **断言"没用时不掺假"**。
   - `emulate_func` 不给 `dump` 时**必须没有** `memory` 字段（旧行为不变）
   - `call_graph` 关掉 `include_vtable` 后**必须归零**（证明能力可控、不是恒真）
   - `xref_enhanced` 的代码侧 `refs` 查询**仍必须是 0**（没有 adrp 就是没有，
     不能为了"看起来有用"把 indirect 混进 refs）

3. **交叉验证**：`call_graph` 报出的每个槽，都再用 `vtable_at` 独立复核一次
   （`is_vtable` 为真 且 `target` 等于声称的目标）。

## 七、兼容性

| 老调用 | 变化 |
|---|---|
| `emulate_func` 不给 `dump` | 不变（无 `memory` 字段） |
| `call_graph` | 返回新增 `vtable_edge_count` / `indirect_only` / 节点 `vtable_in`；`include_vtable` 默认 true |
| `xref_enhanced` | 返回新增 `indirect` 一节；原有 `refs` / `suspicious` 语义不变 |
| `string_crack` | 结果**更多**（修复了全 0）；`addr` 行为变了（不再静默退全库）；新增 `plaintext` 模式 |
| `sensitive_scan` | 结果**更少但更准**；返回结构从 `{kind: [items]}` 变为 `{kind: {count, items}}`，并新增 `filtered` / `params` |

> ⚠️ `sensitive_scan` 的返回结构变了（列表 → 带 count 的字典）。
> 这是有意为之：原来"列表为空"和"没扫到东西"不可区分。
> 仓库内没有其它代码依赖这个结构（已 grep 确认）。
